# 流式全状态指纹设计

日期：2026-08-29

## 实施结果

最初的纯 GDScript 通用递归 accumulator 在 512 状态微基准中只有旧算法的
`0.543x`，证实逐元素 Variant 分派、临时排序项和 Callable 调用抵消了避免
大字符串的收益。生产路径因此在不改变本设计“完整 payload、固定深度语义
不变、128 位有限指纹”的边界下，改用 Godot 原生 Variant 二进制编码和
原生 SHA-256，截取前 128 位并保留编码字节长度。通用递归指纹器仅保留给
固定 Variant 结构向量测试。

最终微基准为 `16.49x`（`1328.7` 对 `80.6` keys/s）；同机 14 开局十秒
生产档案的合计吞吐从 `246.09` 提升到 `411.09` nodes/s（`+67.05%`），
每节点状态键计时下降 `93.23%`，深度二完成数从 `0/14` 变为 `2/14`。
14 个开局的深度一评分、根动作和 exact-state digest 全部一致，且无
fallback。该实测偏差取代下文对生产递归 accumulator 的原始实现假设；
其余状态覆盖、正确性和验收约束保持有效。

## 背景

生产 AI 使用 `DuelSearch` 的 LazyOnly 完整轮次迭代加深搜索。最近一次
生产开局剖析显示，状态键构造约占搜索时间的 `43.8%`，是最大的单项
热点；模拟器转移与状态复制约占 `38.1%`。当前
`DuelStateKey.build_compact()` 会先用通用递归编码构造完整 canonical
字符串，将所有文本转成十六进制，再对完整字符串及其反转分别调用
字符串 hash。卡牌描述、背景文字、图片路径和完整能力声明都会在每个
搜索节点重复参与分配、拼接和哈希。

纯 PVS 消融没有改善这一瓶颈：Lazy+PVS 相比 LazyOnly 只减少 `0.7%`
节点，却增加 `5.0%` 搜索时间。下一项优化因此选择方案 A：保持现有
全状态覆盖，只改变 compact key 的编码方式，不排除任何字段，也不要求
模拟器维护增量指纹。

## 目标与成功标准

本轮目标是在不改变固定深度搜索语义的前提下，减少状态键构造成本。

必须同时满足以下条件才算通过：

1. 14 个真实 Quick 开局的固定完整轮次深度评分与根动作全部保持一致。
2. 测试状态语料中的新指纹碰撞数为零。
3. 所有开局仍至少完成完整轮次深度一，且不增加 fallback。
4. 相同机器、开局、十秒预算和 Dummy 音频条件下，14 开局的合计搜索
   吞吐相对本轮改动前的新测基线至少提高 `20%`。合计吞吐定义为总搜索
   节点除以总搜索秒数，不使用各开局百分比的简单平均。
5. 每节点 `time_key_usec` 必须低于基线，并与吞吐变化方向一致；它是归因
   检查，不另设独立百分比门槛。
6. 搜索相关测试和完整自动化套件全部通过。

是否有开局在十秒内完成完整轮次深度二只作为附加观察，不是硬门槛。

## 非目标

- 不排除描述、图片或任何展示字段。
- 不建立按卡牌 ID 定制的搜索知识。
- 不改变评估器、行动排序、PVS、战术延伸或搜索深度语义。
- 不改变 `DuelSimulator` 的规则转移。
- 不给 `DuelState` 增加 dirty 标记或增量哈希字段。
- 不实现紧凑模拟器、复制时写或语义裁剪状态键。
- 不要求新 compact key 与旧 compact key 的文本相同。
- 不把 compact key 写入存档或建立跨版本持久化兼容。

## 架构

### 统一状态 payload

`DuelStateKey` 提取一个私有 `_state_payload(state)`，集中列出当前参与
状态身份的全部顶层字段。`build()` 和 `build_compact()` 都从这个 payload
开始，避免维护两份独立的顶层字段列表：

```text
DuelState
   ↓
_state_payload(state)
   ├─ build()         → 完整 canonical 字符串
   └─ build_compact() → 流式双重指纹
```

`build()` 保留现有精确编码行为，继续供回放、测试、固定 fixture 身份和
调试使用。`build_compact()` 不再调用 `build()`，而是把同一个 payload
交给通用指纹器。

### 通用流式指纹器

指纹器按值结构递归遍历，不构造完整 canonical value 字符串。它维护两组
使用不同种子和混合常量的有序 64 位滚动散列，以及一个结构元素计数。
每一步都吸收类型标记、长度、值或子指纹和当前位置；不能使用单纯 XOR，
因为 XOR 会丢失顺序并允许重复特征抵消。

输出格式固定为：

```text
v2:<结构元素数量>:<hash_a>:<hash_b>
```

`v2` 防止调试期间的新旧 compact key 被误认为同一格式。双 64 位指纹加
结构计数不宣称数学上无碰撞，但碰撞风险应显著低于当前的长度加两次普通
字符串 hash。

该组件必须保持通用和卡牌无关。它不知道棋盘、手牌、卡牌 ID 或能力含义，
只处理 Variant 结构。

## 编码契约

指纹输入遵循以下固定规则：

- `null`、布尔、整数和浮点数使用不同类型标记。
- `String` 和 `StringName` 使用不同类型标记。
- 文本输入为类型、UTF-8 字节长度和原始 UTF-8 字节；不再进行
  `hex_encode()`。
- 数组输入为数组标记、元素数和按索引顺序排列的元素。
- Dictionary 输入为字典标记、键值对数量和稳定排序后的键值对。
- Dictionary 排序继续使用现有 `_encode(key)` 生成的 canonical 排序键。
  这里只编码通常很短的字典 key，不为庞大的 value 构造 canonical 字符串。
- Dictionary 排序后，实际参与指纹的是键本身的类型化结构和对应 value，
  而不仅是排序用文本。
- 未预期的 Variant 类型沿用当前兜底语义：类型编号加稳定文本表示。
- `null` state 使用固定专用 compact key，不与普通状态混合。

数组顺序必须影响指纹；Dictionary 插入顺序不得影响指纹。深复制且语义
相同的状态必须生成相同指纹。`state_version` 继续排除，因为它只用于现场
控制器并发校验，不属于搜索规则状态。

## 碰撞与正确性防护

现有完整 `build()` 是测试判定器。测试状态语料维护：

```text
compact key → exact canonical key
```

如果同一 compact key 对应两个不同的 exact canonical key，测试立即失败，
并报告两个语料来源。该审计用于发现实现错误和可复现碰撞，但不把有限语料
描述成形式化的无碰撞证明。

固定向量和状态测试至少覆盖：

- 空值、布尔、整数、浮点数；
- 空字符串、中文、英文、`String` 与 `StringName`；
- 数组顺序变化；
- Dictionary 插入顺序变化；
- 多层 Array/Dictionary 嵌套；
- 深复制状态；
- 当前每个已纳入 `_state_payload()` 的顶层状态字段；
- 内力、运行时点数、攻击计数、难度、记忆、移除区、效果队列和待选择
  等已有高风险状态差异；
- 真实敌人目录开局及其连续合法转移产生的状态语料。

碰撞审计语料必须覆盖全部 14 个真实 Quick 开局，并用固定顺序的合法动作
转移确定性地产生至少 512 个不同的 exact canonical 状态。达到上限后停止
扩展，保证测试规模固定且可重复。

新增顶层 `DuelState` 字段的流程保持与当前相同：必须显式加入
`_state_payload()` 并添加字段差异测试。新增嵌套 Dictionary 字段会由通用
指纹器自动参与，无须给指纹器添加字段知识。

## 基准与验证流程

### 改动前基线

在修改状态键实现前，运行一次当前代码的 14 开局生产档案。使用当前
LazyOnly 配置、每个开局十秒预算、Dummy 音频和相同开发机器。报告保存在
`.summer/local/ai-benchmarks/`，不提交 Git。

同一基线阶段还要保存一份忽略的固定深度快照。每个真实 Quick 开局记录
开局 ID、根行动方、完整轮次深度一评分和根动作 canonical key。改动后的
等价验证逐项读取这份快照比较，不能只比较两个都已经使用新状态键的搜索
档位。

基线至少记录：

- 总节点、总搜索秒数和合计节点/秒；
- `time_key_usec` 总量及占比；
- 每个开局的完成深度；
- 深度二未完成迭代的根动作进度；
- fallback 和停止原因；
- 当前 compact key 的平均长度。

### 测试驱动实现

先添加期望 `v2` 指纹、稳定排序、类型区分和碰撞审计的测试，并确认它们在
没有新实现时失败。然后实现统一 payload 和流式指纹，依次运行：

1. 状态键与搜索聚焦测试；
2. 真实状态语料碰撞审计；
3. 14 开局固定完整轮次深度动作/评分等价验证；
4. 改动后的同配置生产开局档案；
5. 完整自动化套件。

改动后报告使用与基线相同的统计口径，并额外记录新 compact key 平均长度。

### 通过与失败处理

新实现先作为未提交改动存在。

- 任何动作、评分或规则状态等价失败时，停止性能结论，先修复正确性。
- 正确性通过但吞吐提升不足 `20%` 时，不把结果描述为成功，也不直接提交
  为生产默认。保留证据，由用户决定继续优化方案 A、转向语义裁剪方案 B，
  或撤掉实现。
- 达到所有硬门槛后，才更新 `docs/AI_SEARCH.md` 与 `docs/HANDOFF.md`，提交
  实现和证据摘要。

## 风险

### GDScript 中的散列混合成本

避免字符串分配不保证一定更快；如果每个字节都通过高开销 GDScript 调用
处理，流式实现可能抵消收益。实现应按较大的类型化 token 吸收数据，避免
为每个字节创建 Variant、Array 或 Dictionary。最终只接受真实生产档案的
吞吐证据。

### 整数溢出和平台稳定性

滚动散列必须显式采用 Godot `int` 可预测的 64 位位运算语义，并用固定向量
测试锁定结果。不得依赖 Dictionary 的当前迭代顺序、对象地址或进程随机种子。

### 理论碰撞

置换表只保存 compact key，因此任何有限长度指纹都有理论碰撞风险。双独立
64 位散列、类型/长度编码和结构计数用于把风险降到可接受范围；完整 canonical
键继续保留为测试判定器，而不在生产搜索节点中保存，以免重新引入主要成本。

## 预期结果

本设计优先保持现有的自动全字段覆盖和维护安全性。它不会取得语义裁剪或
增量指纹的理论上限，但应显著降低 UTF-8 十六进制转换、巨型字符串拼接、
完整字符串反转和临时容器分配。是否足以达到 `20%` 总吞吐提升，由同配置
14 开局生产档案决定。
