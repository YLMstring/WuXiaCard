# 原生搜索树第一阶段优化设计

日期：2026-09-03

## 目标

在不改变固定深度 minimax 评分、标准平局动作或任何游戏规则的前提下，减少原生搜索完成 `self_turn` 新深度二所需的节点和时间。

本阶段以 2026-09-03 的四个额外出牌开局为性能基线：

- 东方不败镜像：新深度二耗时 `8.377` 秒；
- 东方不败先手对风清扬：新深度二耗时 `6.777` 秒；
- 风清扬先手对东方不败：十秒完成 `14/35` 个深度二根动作，线性估算 `24.949` 秒；
- 风清扬镜像：十秒完成 `23/35` 个深度二根动作，线性估算 `15.187` 秒。

首要性能目标是让风清扬镜像在十秒内完成新深度二，并将风清扬先手对东方不败的线性估算降至约十八秒或更低。已经完成新深度二的两局不得退回深度一。

## 范围

本阶段包含：

1. benchmark-only 搜索分项计时和排序质量统计；
2. 不改变动作顺序的排序热路径优化；
3. 叶子评价所用的快速合法动作计数；
4. 上一轮完整迭代的树内 PV 动作排序；
5. 本次根搜索内的通用 history heuristic。

本阶段不包含置换表、PVS、killer heuristic、lazy 动作分桶、LMR、近似剪枝、多线程、局面评价权重调整、增量状态或 make/unmake。它们必须在本阶段取得独立数据后另行设计。

## 架构约束

- `DuelNativeCompactKernel` 继续是唯一规则与深度搜索实现。
- 所有变化只影响动作排序、统计或等价计算，不新增第二套搜索或规则路径。
- 搜索保持卡牌无关；排序和历史键不得包含卡牌 ID、名称或针对特定能力的分支。
- 只有完整完成的迭代可以替换已发布结果和下一轮 PV 提示。超时或取消的迭代不得污染已完成结果。
- 排序提示永远不能直接复用评分或跳过合法性检查。错误、过期或哈希碰撞的提示最多导致较差顺序，不得影响正确性。
- 生产游戏默认关闭高频计时统计，避免读取高精度时钟本身污染搜索性能。

## 一、搜索分项统计

### 开关

在同一个原生搜索入口增加 `collect_search_diagnostics` 选项。生产默认为 `false`；开局性能脚本和专项测试显式开启。

现有 `NativeSearchStats` 扩展以下累计值：

- 合法动作生成耗时；
- 动作排序耗时；
- transition 结算耗时；
- 叶子评价耗时；
- 状态键计算耗时；
- 其他搜索耗时，由总耗时扣除上述项目得到；
- 发生排序的内部节点数；
- 实际访问的子动作总数；
- cutoff 总数；
- cutoff 子动作位置直方图；
- PV 查询、命中、命中后合法、命中后非法次数；
- history 排序命中和造成 cutoff 的次数。

Cutoff 位置只保留五个固定桶：第一、第二、第三至第四、第五至第八、第九及以后。统计结构大小固定，不按节点分配数组。

关闭统计时，热循环不得调用时钟或构建诊断 Dictionary；现有基本节点、动作、transition 和 cutoff 计数继续保留。

### 报告

`production_opening_depth_profile.gd` 已有的 `time_order_usec`、`time_apply_usec`、`time_evaluate_usec` 和 `time_key_usec` 字段开始接收真实数据，并增加合法动作生成时间、cutoff 桶和 PV/history 命中率。报告继续写入 `.summer/local/ai-benchmarks/`，不得提交。

## 二、排序热路径优化

### 结构分只计算一次

`order_search_actions()` 不再在 `stable_sort` 比较器中重复调用 `action_structural_score()`。每个动作先生成一个临时排序记录：

```text
NativeAction
PV 优先标记
history 分数
结构分数
```

每个分数只计算一次。排序最终仍以 `action_canonical_less()` 打破所有相同优先级，保证确定性。

### 避免动作列表复制

排序函数接管按值传入的动作 vector，调用处通过移动语义交付 `get_legal_native_actions()` 的结果，不再先生成 vector 再完整复制一份。

### 避免冗余字符串转换

同一局面的合法动作中，来源位置相同的动作必然来自同一运行时实例。规范排序不应为这些动作反复执行 `StringName` 到 `String` 的转换。

PV 动作匹配仍必须比较全部字段：动作类型、来源位置、来源实例 ID、目标种类、目标位置和主动能力序号。排序比较优化不得放宽提示合法性。

## 三、快速合法动作计数

新增内部只读函数：

```cpp
int32_t count_legal_native_actions(const NativeState &state, int32_t owner_id) const;
```

它与 `get_legal_native_actions()` 使用完全相同的合法性条件，但只累计数量，不创建 `NativeAction`、复制实例 ID 或分配结果 vector。

`evaluate_baseline()` 的双方行动能力差改用计数函数。真正展开搜索节点、控制器查询合法动作以及动作物化仍使用完整生成函数。

测试必须在真实 Quick 派生状态中对双方验证：

```text
count_legal_native_actions(state, owner)
== get_legal_native_actions(state, owner).size()
```

任何新增激活目标规则都必须同时更新完整生成和快速计数；二者不一致属于集成错误，不允许回退或近似。

## 四、树内 PV 排序

### 两类 PV 数据必须分离

排序提示表只为下一次迭代提供首选动作。它以完整局面的 state-only checksum 为键，不包含剩余搜索边界。深度增加后仍可命中上一轮访问过的相同局面。

现有同回合额外出牌计划继续使用“局面＋剩余回合边界”的严格键。它决定一个动作是否可以在实际对局中直接复用，因此不得与宽松的排序提示表合并。

### 迭代生命周期

每轮迭代维护：

- `previous_iteration_ordering_moves`：上一轮完整迭代的排序提示；
- `current_iteration_ordering_moves`：本轮每个已完成内部节点的最佳动作；
- 现有 `iteration_principal_actions`：用于严格主变化及同回合计划。

节点生成动作后查询上一轮提示。只有找到字段完全相等且当前合法的动作时才排第一。当前迭代完整完成后，两张排序表交换；若超时、取消、原生拒绝或没有完整根动作，本轮表直接丢弃。

状态 checksum 在节点内最多计算一次，并在排序提示和严格 PV 存储间复用，避免为了新增提示重复哈希整个状态。

## 五、History heuristic

History 只在一次根搜索调用内存在，不跨对局、存档或 AI 决策持久化。

### 历史键

键由通用动作及来源状态组成：

- 动作类型；
- 目标是棋盘格还是手牌槽；
- 主动能力使用来源棋盘格；手牌出牌统一使用一个固定的“手牌来源”哨兵值，不使用物理手牌槽编号；
- 目标位置；
- 主动能力序号；
- 来源牌当前四边点数；
- 当前内力；
- 当前有效能力数量。

键不得包含卡牌 ID、名称或运行时实例 ID。物理手牌槽编号也不得进入 history 键，因为槽位占据者可能变化；不同手牌通过来源牌的四边点数、内力、能力数量和动作目标等通用运行状态特征区分。两个运行状态特征完全相同的手牌可以共享 history，这只影响排序。

### 更新与衰减

只有真正触发 `beta <= alpha` 的动作获得奖励：

```text
bonus = (remaining_owner_turn_boundaries + 1)²
```

分数使用有界整数并饱和写入。每次开始新的公开深度迭代时，将所有历史分数衰减至原来的 `75%`，避免早期偶然 cutoff 永久支配顺序。

第一版只奖励 cutoff 动作，不惩罚此前失败动作，也不增加 killer、countermove 或跨搜索持久历史。这些扩展只有在数据表明 history 命中不足时才重新讨论。

### 排序优先级

完整优先级固定为：

```text
上一轮精确 PV 动作
→ history 分数
→ 当前结构分数
→ 标准动作编号
```

History 只影响搜索顺序。固定深度 minimax 的最终评分和标准平局动作必须与关闭 history 时一致。

## 配置与消融

同一个原生搜索实现增加三个显式选项：

- `use_internal_pv_ordering`；
- `use_history_ordering`；
- `collect_search_diagnostics`。

前两个在完成正确性与性能门槛后成为生产默认值；统计始终默认关闭。测试和基准可以单独关闭前两个，形成结构排序参考组。它们不得选择不同的规则执行、评价函数、深度语义或 alpha-beta 实现。

## 正确性与故障处理

必须覆盖：

1. 快速动作计数在真实状态中与完整生成完全相等；
2. 关闭和开启 PV/history 时，固定深度评分与标准根动作完全一致；
3. 平分局面仍选择规范最小动作；
4. 过期、非法或哈希碰撞的 PV 提示被忽略；
5. 被超时或取消打断的迭代不替换上一个完整结果；
6. 额外出牌计划仍只在完整深度二及以上、严格状态匹配时复用；
7. unsupported transition 继续作为集成错误返回，不得因排序提示而跳过；
8. 重复搜索的内存占用回落并保持稳定；
9. 完整自动化套件通过。

固定深度一致性通过同一原生 minimax 的结构参考排序和候选排序进行 A/B。不得仅用十秒内选中动作相同代替固定深度证明，因为超时可能让两组完成不同迭代。

## 实施与测量顺序

1. 接入诊断统计，确认统计关闭时结果和速度无回归；
2. 实施结构分预计算、动作 vector 移动和规范比较优化；
3. 实施快速合法动作计数；
4. 运行一次四开局 `self_turn` 十秒里程碑；
5. 实施树内 PV，使用开关与结构参考组做固定深度消融；
6. 运行第二次四开局里程碑；
7. 实施 history，完成最终消融和四开局测量；
8. 运行重复搜索内存回归；
9. 运行完整测试套件；
10. 进行静音生产路径检查并更新 `docs/AI_SEARCH.md` 与 `docs/HANDOFF.md`。

刚生成的两份四开局报告是阶段前基线，不再在改代码前重复运行。局部实现先用固定深度和微基准验证，只在上述里程碑重新运行四个十秒开局。

## 验收标准

必须满足：

- 所有固定深度参考评分与标准动作一致；
- 四局均无 fallback、unsupported 或无效动作；
- 已完成新深度二的两局继续完成；
- 完整测试套件通过；
- 重复搜索无持续内存增长；
- Android 所需生产默认路径不启用高频诊断计时。

性能目标为：

- 风清扬镜像在十秒内完成新深度二；
- 风清扬先手对东方不败的线性估算降至约十八秒或更低；
- 各子优化通过开关消融确认贡献，明显无收益或稳定退化的代码不进入生产默认配置。

若本阶段未达到第二个性能目标，后续按实测数据决定优先进入置换表重复率探针、PVS 还是更深的节点执行优化，不通过修改评估权重或引入未经批准的近似剪枝追赶指标。
