# 2026-09-07 原生结算栈与循环终局设计

## 目标

将 `DuelNativeCompactKernel` 中会互相嵌套的规则结算改为显式、堆上管理的
后进先出结算栈，消除长效果链耗尽 Android 原生线程调用栈的风险，同时保持现有
卡牌规则、触发顺序、目标锁定方式和展示事件顺序不变。

本次同时增加结算循环终局：当规则结算第一次回到完全相同的结算配置时，停止该
循环，保留此刻局面并立即按当前场面计分。除两个正常终局外，结果提示直接在原有
胜负与比分文本前写明终局原因。

## 选定方案

采用完整显式结算栈，而不是只改攻击、进场、翻面和移除，也不采用先进先出的事件
队列。

- 只迁移主要生命周期仍会让事件、动作序列、移动、抽牌和弃牌彼此递归，不能保证
  不再发生原生栈溢出。
- 普通事件队列会把当前的深度优先结算改成广度优先，改变大量卡牌的嵌套时点。
- 显式 LIFO 栈可以逐步恢复当前递归函数的 continuation，保持行为等价，并把深度
  上限从原生调用栈转移到受控的堆内存。

AI 的 minimax、PVS、迭代加深和置换表不属于这套结算栈。搜索仍可保留自己的递归；
每次搜索动作调用同一套迭代式规则结算器。此次 Android 崩溃涉及的是单次规则转移
内部的同步递归，而不是搜索树层数本身。

崩溃报告中显示的 512 个原生调用帧是回溯工具的输出上限，不是规则递归次数，也不是
低于 512 帧便安全的运行阈值。真正的限制是设备线程栈占用的字节数；一次规则嵌套可
展开为多个大小不同的 C++ 调用帧，实际栈还可能在回溯截断处之后继续。因此不能用
“限制到 511 次”或类似数量代替本设计。

## 结算器边界

新增原生内部 `ResolutionEngine` 概念。它不是 Godot-facing 类，不进入 `DuelState`，
也不暴露给 GDScript。一次公开动作转移建立一个引擎，向其压入根任务，然后循环：

1. 查看栈顶帧。
2. 执行该帧的一个最小阶段。
3. 若阶段需要先完成子结算，将 continuation 留在原帧并把子帧压到栈顶。
4. 子帧完成后恢复原帧。
5. 完成的帧弹出。
6. 栈清空后物化当前状态和按顺序生成的展示事件。

帧只保存纯原生数据，例如卡牌引用、格子、事件上下文、动作索引、目标快照和当前
阶段。不得保存 Godot 场景节点、Control、Tween、音频对象或其它展示层引用。

## 栈帧划分

### 1. 动作序列帧

负责按声明顺序执行一组已编译 action，并保存下一条 action 的索引。嵌套
`ACTION_FOR_EACH_SELECTED_CARD` 使用同一类序列机制：选择阶段按现有规则取得目标
快照，之后逐张重检并执行其子动作。

该帧替代 `execute_actions()`、`execute_actions_with_state()`、
`execute_for_each_selected_card()` 等函数之间的递归调用。目标是预先锁定还是每次读取
结算后的当前目标，完全沿用每个现有原语的语义。

### 2. 事件帧

负责一个完整规则事件节点，包括 `CARD_SUMMONED`、`CARD_AFTER_SUMMONED`、
`CARD_BE_ATTACKED`、`CARD_AFTER_FLIPPED`、`CARD_BEFORE_EXILED`、回合开始和回合结束
等事件。

事件帧保存：

- 事件类型与纯数据事件上下文；
- 已按现有稳定顺序发现的触发项；
- 下一项触发索引；
- 触发能力的稳定身份，而不是易受数组换位影响的当前位置。

每项能力在真正结算前仍按现有规则重新验证来源实例、能力是否存在、所属方、位置和
条件。能力数组中前项被删除或换位，不会仅因索引变化而令已发现的另一项错误失效。

### 3. 进场帧

负责完整进场生命周期：

1. 验证牌与目标格并放置。
2. 记录进场展示事件。
3. 结算 `CARD_SUMMONED`。
4. 若原进场实例仍在场，重新进行全场发现并结算 `CARD_AFTER_SUMMONED`。
5. 再次验证实例和进场期间状态。
6. 决定是否执行标准进场攻击。
7. 完成进场。

保留以下既定规则：

- `CARD_AFTER_SUMMONED` 检查全场。
- 手牌进场牌在 `CARD_SUMMONED` 中被换到别处，只要同一实例仍在场，仍可进入
  `CARD_AFTER_SUMMONED` 窗口。
- 进场过程中只要该实例曾经翻面，即使后来翻回最初阵营，也取消标准攻击。
- 进场后的所属方、位置、能力与攻击目标仍在各自既有时点重新验证。

### 4. 攻击帧

负责一次指定或标准攻击的完整过程：

1. 按当前策略生成并保存目标顺序。
2. 对准备攻击的目标进行首次合法性和点数比较。
3. 结算 `CARD_BE_ATTACKED`。
4. 重新确认目标实例仍存在且仍可被本次攻击命中。
5. 执行翻面或特殊攻击结果。
6. 完成由结果产生的全部子事件。
7. 继续预先锁定目标列表中的下一项。
8. 最后结算确实发生过攻击所对应的攻击后能力。

保留以下既定规则：

- 点数比较对每个候选目标只在最初进行一次；通过后不因中途点数变化重新比较。
- 目标在 `CARD_BE_ATTACKED` 中被移除或变得不可攻击时，本目标结束，不另找替补。
- 无限范围目标移动不会单独使攻击失效。
- 攻击者在攻击循环中途翻面后，剩余目标不再攻击。
- 指定攻击成功开始时也计入每方每回合最多二十次攻击的限制。

### 5. 翻面帧

负责一次已提交翻面的完整生命周期：

1. 结算翻面前事件与防止翻面。
2. 若未被阻止，改变所有权。
3. 失去所有非保留、且非“自身翻面后触发”的旧能力。
4. 结算 `CARD_AFTER_FLIPPED`。
5. 失去旧的、未标记保留的“自身翻面后触发”能力。
6. 完成翻面记录。

新获得的能力不属于最后一步的旧能力清理集合。翻面防止、金色 ki bead 等规则不随
此次重构改变。

### 6. 移除帧

负责：

1. 锁定待移除实例、原区域、原格子和移除原因。
2. 结算 `CARD_BEFORE_EXILED`。
3. 重新确认该精确实例仍处于可由原请求移除的上下文。
4. 真正进入所属方移除区。
5. 记录移除展示和所需快照。
6. 结算移除后事件。

四边降为零、攻击效果、能力主动移除等原因继续作为纯数据上下文传递。类似玉碎昆冈
在移除前暂离并重进场后，外层请求会因精确上下文失效而自然停止，不产生
`card_exiled`。

### 7. 移动与换位帧

单张移动和换位的每一个概念移动腿依次执行：移动前事件、重新验证、实际改变位置、
移动后事件。两张牌换位不会并发修改位置；其 continuation 明确记录当前进行到哪一
条腿。

这样既维持泰山十八盘、金刚伏魔圈等规则顺序，也保证控制器收到的移动、点数变化、
移除和进场展示事件天然按结算顺序排列。

### 8. 抽牌、弃牌与区域转换帧

以下会产生后续事件的区域变化进入结算栈：

- 逐张抽牌；
- 单张和批量弃牌；
- 从手牌进场；
- 从移除区或暂离区重新进场；
- 返回手牌；
- 获得新实例、目录新鲜复制或完整运行时复制；
- 空牌库抽牌时补入太祖长拳。

批量弃牌继续先锁定精确实例，把选中牌全部放入弃牌区，再按物理手牌顺序逐张结算
自身弃牌链，最后只发出一次批量完成事件。普通区域容器修改可保留为无递归的直接
辅助函数；任何由其引起的规则事件必须压入帧，不能同步调用另一条生命周期。

### 9. 点数与内力后果帧

直接加减点数或内力仍是普通原子操作，不为每次数字写入单独分配帧。若修改产生规则
后果，则把相应任务压栈：

- 四边降为零产生移除帧；
- 内力变化或点数变化产生事件帧；
- 支付内力后继续能力动作；
- 多张牌同时变化继续生成同一批展示事件，并保持变化前停顿和并行动画语义。

四边均为 `-1` 的特殊语义及其不可被自动点数变化选中规则保持不变。

### 10. 回合边界帧

负责动作完成后的根级流程：

1. 更新行动数和当前所属方回合内计数。
2. 决定是否继续本回合已经获得的额外出牌。
3. 结算回合结束事件。
4. 完成所属方回合边界并记录场面重复签名。
5. 在下个回合开始前判断终局。
6. 未终局时才切换并结算下个回合开始事件。
7. 没有可用行动时只跳过行动，仍完整经过回合开始和结束节点。

达到行动上限后不截断当前回合及已经获得的额外出牌。每回合最多获得一次额外出牌
的现有规则保持不变。

## 不进入规则结算栈的模块

下列逻辑保持普通无副作用查询或原子辅助函数：

- 条件和 selector 判断；
- 卡牌、格子、所属方与相邻关系查询；
- 攻击目标策略构造和首次点数比较；
- `can_change_powers()` 等规则谓词；
- 目录声明编译和支持度检查；
- 状态载入、物化、序列化和展示快照组装；
- 终局计分、战略评估和结构排序评分；
- 状态键、置换表、history、PV 和搜索统计；
- GDScript 控制器、动画、音频和场景节点。

这些函数不得反向同步进入规则生命周期；需要继续结算时只能由调用帧压入新任务。

## 循环检测语义

### 检测对象

循环比较的是完整“结算配置”，而不是仅比较九宫格：

```text
规则状态指纹 + 待结算帧栈指纹
```

规则状态指纹包括双方所有区域、每张牌的规则相关运行时数据、所属方、位置、点数、
内力、有效能力状态、当前行动方、回合内限制、额外出牌状态和其它会影响后续规则的
字段。

帧栈指纹包括每个帧的类型、阶段、下一项索引、锁定目标、事件上下文和 continuation。
只有当前状态相同且接下来待做的工作也相同，才构成结算循环。单纯再次出现相同棋盘
但手牌、能力、内力或待结算任务不同，不属于该终局。

### 实例身份规范化

不能直接把递增的 `instance_id` 数值作为循环等价条件，否则不断创建同目录 ID 新实例
的循环永远不会重复。循环指纹在一次根结算内部按各区域和帧引用首次出现顺序，为仍
可达的实例建立规范化编号。卡牌之间的“引用同一实例”关系必须保留，但实际分配的
整数值不参与等价比较。

展示事件、动画数据、提示文本、诊断计数和搜索统计不进入循环指纹。

### 命中处理

每次根结算开始时记录初始配置，并在每个帧最小阶段完成、状态与 continuation 都稳定
之后检查配置。第一次发现本次根结算已经出现过的等价配置时：

1. 保留当前这个首次重复出现的局面，不回滚。
2. 清空尚未执行的结算帧。
3. 不再触发回合结束、下回合开始或 `TRIGGER_BEFORE_DUEL_END`。
4. 设置不可逆的终局原因 `RESOLUTION_LOOP`。
5. 立即按当前场面牌数执行现有终局计分和胜负判断。

循环历史仅存在于本次规则转移的 `ResolutionEngine` 中，不进入存档、回放或 AI 置换
表。终局原因进入物化状态，以便玩家对局、AI、回放和控制器得到同一结果。

实现可另设一个极高的内部步骤保险，只用于把未能识别的实现错误转成明确诊断，不能
把该保险冒充“相同状态循环”或正常比赛规则。

## 终局原因与界面文本

原生状态增加紧凑终局原因枚举。`is_terminal()` 首先识别已经锁定的强制终局原因，
再执行现有回合边界判断。终局后原因不可被后续查询覆盖。

两个正常终局不在界面上显示原因：

- 九宫已满；
- 双方均无可用行动。

三个非正常终局把原因直接合并进原有胜负和比分文本，不另起一行，也不丢失任何原有
结果信息：

```gdscript
"行动上限 获胜 · %d–%d" % [player_total, opponent_total]
"五次重复 获胜 · %d–%d" % [player_total, opponent_total]
"结算循环 获胜 · %d–%d" % [player_total, opponent_total]
```

失败和平局分别将“获胜”替换为“失败”和“平局”，比分始终保持玩家在前、敌方在后。
回放保存并使用实际终局原因，不根据最终棋盘重新猜测。正常终局继续显示当前已有结果
文本。

## 文件职责

继续沿用现有 C++ 源文件边界：

- `duel_native_compact_kernel.cpp`：建立根结算器，公开动作入口和最终物化。
- `duel_native_events.cpp`：事件帧的发现、重检和推进。
- `duel_native_actions.cpp`：动作序列、选择器循环、抽弃牌、区域转换、点数和内力后果。
- `duel_native_resolution.cpp`：进场、攻击、翻面和移除帧。
- `duel_native_lifecycle.cpp`：移动/换位、回合边界、终局原因和计分。
- `duel_native_policy.cpp`：保持纯查询，不拥有或推进结算栈。
- `duel_native_search.cpp`：保持搜索职责，只调用公开规则转移。
- `duel_native_compile.cpp`：保持声明编译职责。

共享帧枚举、纯数据 payload、规范化循环指纹和 `ResolutionEngine` 内部接口放在原生私有
头文件中，不扩张 GDExtension 公共 API。

## 行为与性能约束

- 结算顺序和展示事件序列必须与当前生产路径一致，循环终局除外。
- 搜索和玩家必须调用同一个结算器，不增加 GDScript 规则回退。
- 卡牌目录声明不因重构改写，搜索代码不得添加卡牌 ID 特判。
- 帧 payload 使用紧凑原生结构和索引，避免在每一步复制完整 `Dictionary` 或完整状态。
- 循环指纹采用增量或紧凑原生编码；不得为每个步骤物化 Godot `Dictionary`。
- 规则栈是每次动作转移的短生命周期对象，完成后必须释放；不得累计到跨对局状态。
- Android 和桌面继续使用相同规则实现。

## 迁移期等价策略

迁移期间暂时保留当前递归式原生结算器作为测试 Oracle，但它不重新接入玩家、测试
模式、greedy fallback 或 AI 的生产路径，也不允许继续为它单独实现新规则。测试构建
可以把完全相同的初始状态和动作分别交给新旧原生结算器，并逐项比较：

- 完整最终规则状态，而不只比较棋盘；
- 展示事件的内容与严格顺序；
- 下一步合法行动集合；
- 连续多步确定性对局中的每个动作边界；
- 搜索所需的精简事件路径与完整玩家路径。

结算循环是唯一预期行为差异：旧路径可能无限递归或触发保护性中止，新路径必须在完整
结算配置首次重复时以 `RESOLUTION_LOOP` 终局。此类用例不要求旧路径跑到崩溃，而是
验证新路径能够识别循环、保留重复时局面并产生正确结果文本。

迁移顺序按生命周期逐类推进。每迁移一类帧，先完成该类针对性等价测试，再继续下一
类；生产仍保持单一已选路径。全部帧、完整套件、迁移封印对局、高风险深链以及 Android
实机验证通过后，删除旧递归结算器和测试开关，避免形成长期维护的第二套规则。

## 验证要求

### 单元和等价测试

1. 为每种帧生命周期增加顺序测试，覆盖正常完成、来源失效、目标失效和子结算恢复。
2. 复用现有规则/卡牌单元测试，确认所有展示事件顺序和最终状态不变。
3. 增加深链压力用例，证明数千层等价嵌套不会增加原生调用栈深度。
4. 增加创建新实例但语义重复的循环，验证规范化身份仍能命中。
5. 增加“棋盘相同但手牌、能力、内力或待处理帧不同”的反例，确认不会误判。
6. 验证循环命中保留重复时局面、丢弃剩余帧、不触发回合边界或终局前能力。
7. 验证行动上限、五次重复、结算循环的胜/负/平三种精确提示文本。
8. 验证九宫已满和双方无行动仍使用原有文本，不显示终局原因。
9. 迁移期间对新旧原生结算器执行逐动作状态、展示事件和合法行动的自动差分；循环
   终局按上述预期差异单独断言。

### 集成与回归

1. 运行完整 canonical 测试套件。
2. 运行玩家生产路径、测试模式和 AI 搜索路径的同局面等价测试。
3. 重跑曾触发 Android 栈溢出的高风险卡组组合及额外出牌压力局。
4. 在静音 Android 实机上连续进行多局并观察崩溃、内存和帧时间。
5. 记录固定深度搜索的动作、评分、节点数和耗时，确认规则等价且性能没有不可接受的
   回退。
